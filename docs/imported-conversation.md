技术上，个人网站一般有三种合理架构：

| 方案 | 适合情况 | 特点 |
|---|---|---|
| 静态网站 | 作品集、博客、个人主页 | 快、便宜、安全、维护简单 |
| CMS 驱动 | 经常发布内容，不想改代码 | 后台编辑方便，但系统更复杂 |
| 全栈应用 | 登录、付费、社区、复杂交互 | 能力最强，但开发和维护成本最高 |

对大多数个人网站，我的默认建议是：

- 前端采用静态生成或服务端渲染
- 项目和文章先使用 Markdown/MDX 管理
- 图片放在站点资源目录或对象存储
- 联系表单使用托管表单或轻量接口
- 暂时不引入数据库和用户系统
- 部署在带 CDN、HTTPS 和自动发布的平台
- 从一开始保留 SEO、访问统计和内容迁移能力

这样第一版足够轻，未来需要 CMS、数据库、多语言或会员功能时也能逐步增加，不必一开始承担复杂度。

为了确定你的架构，先回答最关键的问题：**你希望访问者来到网站后，最主要做什么？** 例如了解你、看作品、阅读文章、联系合作，还是购买服务？

### 首页应该回答的四个问题

访客进入网站后，最好能在一分钟内知道：

1. 你是谁？
2. 你擅长什么？
3. 你做过哪些有说服力的项目？
4. 如何联系你？

因此，首页不宜写成完整履历，而应该是精炼的“个人摘要”。详细内容放到经历页和项目详情页。

### 经历与项目应当分开

两者承担不同作用：

- 经历页展示你的发展轨迹，强调时间、角色和成长。
- 项目页展示你的实际能力，强调问题、行动、贡献和结果。

项目不要只写“使用了哪些技术”或“完成了哪些功能”，更有说服力的表达结构是：

> 在什么背景下，遇到了什么问题，我负责什么，做出了哪些关键决策，最后产生了什么结果。

如果项目很多，首页只展示最具代表性的 3–6 个，其余放进完整项目列表。

### 第一版建议控制规模

首个版本可以只做：

- 首页
- 项目列表
- 项目详情
- 关于/经历页
- 联系入口
- 中英文切换暂缓，除非你的受众明确包含海外用户
- 博客暂缓，除非你已经有持续发布的内容

技术上暂时不需要数据库或复杂后台。个人经历和项目可以作为结构化内容文件保存，以后再接 CMS。

接下来最影响页面结构的问题是：**这个网站主要给谁看？** 是招聘方、潜在客户、同行、学校申请人员，还是泛社交关系？另外，你希望他们看完之后优先联系你、下载简历，还是继续浏览项目？

## 项目页也不要写成简历条目

简历中的项目通常是：

> 负责某系统开发，使用 A、B、C 技术，实现若干功能。

网站中的项目案例应该有故事和判断：

```text
背景 → 问题 → 约束 → 决策 → 实现 → 结果 → 反思
```

真正体现个人差异的通常不是最后用了什么技术，而是：

- 你为什么这样定义问题
- 你面对过哪些限制
- 你做了什么关键取舍
- 哪些部分是你的贡献
- 结果是否可以量化
- 如果重做一次会怎样改变

## 中英文架构

建议中英文采用独立路径：

```text
/zh/                 中文首页
/zh/projects/        中文项目列表
/zh/projects/name/   中文项目详情
/zh/about/           中文关于页

/en/                 English home
/en/projects/
/en/projects/name/
/en/about/
```

语言切换时应留在对应页面，而不是每次跳回首页：

```text
/zh/projects/project-a/
        ⇅
/en/projects/project-a/
```

内容管理上，两种语言最好共享同一个内容模型，但分别编写文字：

```text
项目
├── 不分语言：日期、图片、链接、分类
├── 中文内容：标题、摘要、正文
└── 英文内容：title、summary、body
```

这里不建议先写中文再机械翻译。英文版可以更直接、简洁，并根据英语读者不熟悉的背景补充解释。两种语言表达的是同一个人，但不必逐句完全对应。

还应预留：

- `hreflang` 和独立页面标题，方便双语搜索收录
- 记住访客的语言选择
- 首次访问可参考浏览器语言，但不要强制跳转
- 项目尚未翻译时显示明确状态，不要默默混入另一种语言
- 两种语言使用相同布局，避免维护两套网站

综合来看，我推荐把网站定义为：**以精选项目为证据、以个人故事为连接、以履历为补充的双语个人网站。** 这样它不会变成简历翻版，同时对招聘、合作和个人表达都有效。

## 3D 展示的两个技术层级

### 第一层：标准模型查看器

适合以下需求：

- 鼠标或触摸旋转
- 缩放和平移
- 自动旋转
- 切换动画
- 全屏浏览
- 热点标注
- 移动端 AR 查看
- 调整基础材质和环境光

可以使用 `<model-viewer>`。它专门用于网页中的 GLB/glTF 模型，支持现代桌面和移动浏览器，并提供 WebXR、Android Scene Viewer 和 iOS Quick Look 等 AR 路径。[官方说明](https://modelviewer.dev/)  

优点是开发成本低、移动端兼容性较好，适合作为第一版。

### 第二层：定制化 3D 场景

如果你想实现：

- 点击模型部件查看说明
- 爆炸视图
- 剖面展示
- 材质或配色切换
- 多个模型组成场景
- 镜头引导和滚动叙事
- 自定义光影、粒子和着色器
- 模型与页面文字联动
- 虚拟展厅或沉浸式作品空间

则使用 Three.js，或者在 React 架构中使用 React Three Fiber。Three.js 的 `GLTFLoader` 支持 glTF/GLB、动画以及 Draco、Meshopt、KTX2 等压缩和扩展能力；它当前以 WebGL 2 进行渲染。[Three.js GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html) · [WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html)

React Three Fiber 则把 Three.js 场景封装为 React 组件，并提供模型加载与加载进度等能力。[官方模型加载文档](https://r3f.docs.pmnd.rs/tutorials/loading-models)

## 性能与降级策略

3D 展示最容易出现的问题不是“能否实现”，而是模型在手机上是否流畅。因此架构里需要明确：

- 页面先显示封面图，用户进入视区或点击后才加载模型。
- 同一页面只激活一个主要 3D 场景。
- 对高面数模型制作网页优化版本。
- 使用压缩网格和压缩纹理。
- 限制阴影、实时反射与透明材质。
- 检测不支持 WebGL 2 或性能不足的设备。
- 加载失败时展示转台视频或高质量静态图。
- 提供加载进度、模型大小和“点击加载”提示。
- 页面切换后主动释放模型、纹理和 GPU 资源。

结论是：原来的静态内容架构仍然适用，但项目系统需要升级为**支持按需加载 WebGL 体验的混合前端架构**。第一版用标准查看器解决大多数模型，Three.js 留给真正需要定制交互的重点作品。这样既能做出专业的 3D 展示，也不会让整个个人网站变得笨重。
